Lesson 1 — Teacher Modelling Guide

01

Making the Website Work for Real Users

Week 3 · 60 min · comfort_status() function · web_page() HTML redesign

0–10 minLaunch
10–20 minExplore
20–35 minI Do / We Do
35–50 minYou Do
50–60 minFolio

I Do / We Do / You Do breakdown

🎤 I Do (teacher models)

  • Trace data flow on projector with arrows
  • Type comfort_status() live in Thonny
  • Run it in Shell — show all 3 outcomes
  • Think aloud: "I put 30 here because in Queensland heat is a risk above this"

🤝 We Do (guided practice)

  • Students TYPE along (no copy-paste)
  • Pause after each if/elif/else block — students test in Shell before continuing
  • Ask class: "What should we return for 'Getting Warm'?"

✏️ You Do (independent)

  • Students update web_page() HTML independently
  • Sketch layout on paper first
  • Write folio reflection using Worksheet 1 prompts

Opening discussion script — 10 minutes

Teacher says:
"Before we code anything today, I want us to think about who we're actually building this for. Look at the user persona on your worksheet — Aunty Leanne is 62 years old. She uses her phone every day, but she told us she doesn't feel confident with complicated technology. Imagine she arrives at the community room on a hot afternoon and opens her phone to check the monitor. What do you think she actually needs to see?"
Give students 30 seconds to think, then take 2–3 quick responses. Write key words on the board: "clear", "simple", "green/red", "no numbers". These become design criteria the class agrees on together.

Discussion questions

  • 1"At the moment, our website just shows numbers — 24.5°C and 67%. Would Aunty Leanne know if that's safe? Why not?"
  • 2"What does 'comfortable' actually mean for a 62-year-old Elder sitting in a room for 2 hours? Is 28°C comfortable for you? For her?"
  • 3"Our comfort_status function returns THREE values in a tuple. Why might that be more useful than just returning one string?"
  • 4"After we add the status box, our website is better. But is it accessible on a 5-year-old smartphone screen? What would we check?"

Common misconceptions — Lesson 1

MisconceptionWhat to say / do
"The function needs to print() not return" Demonstrate: print() shows in Shell, return passes the value to the caller. Call the function and store the result: result = comfort_status(28,55); print(result). The stored tuple is what the web page uses.
Copying the code without understanding it Ask students to cover the code and explain in plain English: "What does this line do?" before they can continue. Require them to change the thresholds and explain why.
Curly braces {{ }} confusion in f-strings Show side-by-side: {temp} is a Python variable, {{ is a literal brace in HTML (e.g. CSS). Run both in Shell to show the difference. This is a very common crash source.
web_page() only takes 3 arguments (not 6) Walk through the function signature change step by step. Show the old call and the new call — the number of arguments must match. A ValueError message will explain this clearly.

🤝 Support strategies

  • Give Worksheet 1 Part C with blanks already marked — students fill gaps only
  • Seat supported students near teacher during modelling phase
  • Reduce to 2 outcomes first: Comfortable / Not Comfortable
  • Annotated printout: show old code next to new code with arrows
  • Checkpoint: "Before you change web_page(), show me comfort_status() working in Shell"

🚀 Extension prompts

  • "Can you calculate the heat index? Look up the simplified formula."
  • "Add a second page route /history that shows past readings"
  • "Can you make the background colour of the entire page change, not just the box?"
  • "What happens if temp is exactly 30? Which branch runs? Is that correct?"

Wiring Up New Hardware

0–12 minConcept launch

28–45 minWe Do — code
45–55 minYou Do — test
55–60 minFolio

I Do / We Do / You Do breakdown

🎤 I Do (teacher models)

  • Wire button live on teacher breadboard — narrate every step
  • Test in Shell BEFORE adding code — confirm 0/1 values
  • Wire buzzer, test HIGH/LOW
  • Add both to code on projector

🤝 We Do (guided practice)

  • Students wire button while teacher circulates
  • STOP — whole class tests button in Shell together
  • Students wire buzzer — class tests together
  • Add code as a group before releasing independently

✏️ You Do (independent)

  • Test both components with actual sensor readings
  • Photograph breadboard for folio
  • Annotate circuit diagram on Worksheet 2
  • Write folio reflection

Concept introduction script — inputs vs outputs

Teacher says:
"So far, our Pico has only sent information OUT — turning an LED on or off, sending a web page over WiFi. Today we're going to add components that send information IN to the Pico. When someone presses a button, the Pico needs to detect that. This is a digital input — it reads whether there's voltage on a pin or not. One important thing — if a pin is set as an input but nothing is connected to it, it 'floats' — it randomly reads 0 and 1 like a bad coin flip. That's why we use a pull-down resistor. Can anyone guess what it might do?"
Allow 2–3 guesses before explaining: the resistor connects the pin to GND through a high resistance — it holds the pin at LOW (0) until the button physically connects it to 3.3V (HIGH). Draw this on the whiteboard.

Key safety reminder — show before wiring

Wiring safety — tell students every time

Always disconnect USB before adding or moving wires. Only reconnect after the wiring has been checked. The Pico W's 3.3V pins can be damaged if shorted directly to GND without a resistor. The active buzzer does NOT need a resistor — it has its own internal limit. Never connect the buzzer + pin directly to 5V or the computer's USB power — always use a GPIO pin.

Discussion questions

  • 1"Why do we use a SHORT beep (0.3 sec) for the buzzer rather than leaving it on while the room is too hot?"
  • 2"If Aunty Leanne is already in the room when it becomes too hot, should the system buzz every loop iteration? What would that be like?"
  • 3"The button currently prints a message and flashes the LED. How would you make it actually force a fresh web page to load?"
  • 4"Look at the Pin.PULL_DOWN constant. Can you find Pin.PULL_UP in the MicroPython docs? When would you use that instead?"

Common misconceptions — Lesson 2

MisconceptionWhat to say / do
Buzzer buzzes constantly and won't stop Almost always: missing buzzer.value(0) after the sleep, OR the except block doesn't turn it off. Show the fix live — and explain: always put buzzer.value(0) in the except block too, so any crash turns it off.
Button always reads 1 even when not pressed Pull-down resistor is missing or connected to wrong row. Check: the resistor should go from the SAME row as GP14 to GND, not a different row. Probe the row in Shell.
Wiring button legs incorrectly (3 or 4 leg confusion) The 12mm button has 4 legs but only 2 unique connections (legs are paired diagonally). Demonstrate which diagonal pair to use. Bridging the breadboard gap ensures you're using different pairs.
Active buzzer polarity reversed The buzzer will be silent (not damaged). The longer leg is always +. If they've already wired it, swap it — Pico W GPIO is current-limited and won't be harmed by brief reverse polarity.

🤝 Support strategies

  • Print A4 wiring diagram — laminate and reuse each year
  • Wire in two separate stages with a teacher check between
  • Give a printed test checklist (Worksheet 2 Part B)
  • Pair weaker students for the wiring phase
  • Do buzzer first (simpler — just + and –) before button

🚀 Extension prompts

  • "Wire a second LED on GP12 — make it light red automatically when 'Too Hot'"
  • "Add the photocell on GP26 (ADC) — what new information does this give Aunty Leanne?"
  • "Can you make the buzzer only beep once per status change rather than every loop? You'll need a variable to track the previous status."

Lesson 3 — Teacher Modelling Guide

03

Testing, Debugging and Documenting

Week 5 · 60 min · Systematic test table · Bug hunt · Thonny debugging techniques

0–10 minConcept launch
10–25 minBug hunt demo
25–50 minTest table
50–60 minImprove + folio

Bug hunt — demonstrate on projector, students work on Worksheet 3 Part A

Teacher says:
"I'm going to show you three broken programs. Without running them, I want you to look at the code and — in pairs — write down what you think the problem is and what error message Thonny would show. You have 2 minutes."
Show each bug on the slide (these are in Slide 15 of the PPTX). After 2 minutes, ask pairs to share. Then reveal the fix. Key learning: students should be able to read an error message and work backwards to the cause — this is a core programming skill at the Year 10 band.

Discussion questions

  • 1"If you just run the code and it works, have you tested it? Why or why not?"
  • 2"Look at Test 7 in the test table — 'unfamiliar user understands the page.' Why is this a valid test for a digital system?"
  • 3"What's the minimum number of tests needed to properly test the comfort_status() function? Think about edge cases — what if temp is exactly 30?"
  • 4"Your test table is folio evidence. What does a 'fail' result in your test table actually demonstrate about you as a developer?"

Reframing test failures as evidence

Students often hide failures or only test things they know will pass. Explicitly reframe this: a documented failure with a fix demonstrates higher-order thinking and is direct evidence for the "test and refine" criterion. A perfect test table with all passes is suspicious — it likely means the student only tested the happy path.

🤝 Support strategies

  • Pre-fill "What I am testing" and "Expected result" columns — students only fill actual + pass/fail + fix
  • Work through tests 1–4 as a whole class before releasing independently
  • Print bug hunt sheet from Worksheet 3 — students annotate on paper
  • Pair students for the usability test (Test 7)

🚀 Extension prompts

  • "Add edge-case tests: what happens if the sensor is disconnected mid-run?"
  • "Write a test for the trimpot threshold — if you added that extension"
  • "How would a professional developer automate these tests? Research 'unit testing in Python'"

Lesson 4 — Teacher Modelling Guide

04

Evaluating, Reflecting and Presenting

Week 6 · 60 min · Evaluation writing · Folio completion · 3-min video

0–15 minA vs C model
15–30 minWrite evaluation
30–50 minVideo plan + record
50–60 minPeer feedback

Modelling A-grade vs C-grade evaluation — 15 minutes

Teacher says:
"I'm going to read you two evaluations of the same solution. As I read, I want you to notice — which one makes specific claims? Which one links every claim to Aunty Leanne's actual needs? Which one mentions evidence from testing?"
Read both examples from Slide 17 of the PPTX aloud. After each, ask: "What did this evaluation DO that the other didn't?" Build a criteria list on the board collaboratively: specific evidence · linked to user needs · mentions limitations honestly · proposes concrete improvements · compares alternatives.

Discussion questions

  • 1"A limitation is NOT a weakness to hide — it's an honest acknowledgement of scope. What is a real limitation of YOUR solution that would matter to Aunty Leanne?"
  • 2"What would a commercial alternative look like? Think about what's in shops — would it be better or worse for Aunty Leanne? Why?"
  • 3"Your video is 3 minutes. If you spend 2 minutes showing the hardware and 30 seconds evaluating, is that a balanced submission? What does the rubric weight most heavily?"
  • 4"If you didn't have a pull-down resistor, would your solution be reliable? What happens to a system that works 95% of the time in a community health context?"

Connecting evaluation to the rubric — A vs B language

At A: discerning critical evaluation of alternative solutions against stakeholder elicited user stories — students must compare their solution to at least one alternative and reference specific user needs (not just "it works"). At B: effective critical evaluation — strong evidence but comparison may be less developed. Prompt B-range students: "You've described how it works well. Now describe an alternative approach, and explain a drawback of yours compared to it."

🤝 Support strategies

  • Provide the Worksheet 4 Part A sentence starters pre-typed in ClassNotebook — students fill in the brackets
  • Allow video to be split into 3–4 short clips if one take is too much
  • Sit with student during video planning — help them identify 2 specific strengths from their test table
  • Folio checklist: go through every ☐ item individually in a 5-minute 1:1

🚀 Extension prompts

  • "Write 3 formal user stories: 'As Aunty Leanne, I want X so that Y.' Then evaluate each with evidence."
  • "Research a commercial IoT temperature/humidity sensor. Compare price, ease of setup, and cultural appropriateness."
  • "Reflect on one design decision you made early that you would now change. What evidence led you to that conclusion?"
